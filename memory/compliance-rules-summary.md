# Compliance Rules Summary - LLM & Agentic Rules Framework

## Overview

This document summarizes the compliance rules for LLM and agentic systems. The Compliance domain establishes requirements for legal, regulatory, ethical, and audit readiness throughout the AI system lifecycle.

## P0 Critical Rules

### COMP-001: Compliance Assessment

**Rule**: Every AI system must undergo compliance assessment to identify applicable regulations and requirements.

**Why It Matters**: Non-compliance can result in fines, legal action, and reputational damage. Assessment identifies obligations before they become violations.

**Regulations Applicable to AI Systems**:
- GDPR: EU personal data protection
- HIPAA: US health data protection
- PCI DSS: Payment card data protection
- SOC 2: Service organization controls
- EU AI Act: AI system regulation
- CCPA/CPRA: California consumer privacy
- GLBA: Financial data protection
- ISO 27001: Information security management

**Implementation Requirements**:
- Identify jurisdictions where system operates
- Map regulations to system components
- Document compliance requirements
- Assign compliance responsibilities
- Track compliance status
- Update assessment when regulations change

**Evidence Required**:
- Compliance assessment document
- Regulation mapping
- Requirement documentation
- Responsibility assignments

### COMP-002: Evidence Collection

**Rule**: Compliance evidence must be collected, validated, and retained for all required controls.

**Why It Matters**: Without evidence, compliance cannot be demonstrated. Auditors require evidence to verify control implementation.

**Evidence Types**:
- Automated: Generated by CI/CD, evaluation, monitoring
- Manual: Produced by human review, audit, assessment
- Hybrid: Automated collection with human validation

**Implementation Requirements**:
- Define evidence requirements for each control
- Implement automated evidence collection where possible
- Validate evidence completeness and accuracy
- Store evidence securely with integrity protection
- Retain evidence per compliance requirements
- Make evidence retrievable for audits

**Evidence Standards**:
- Timestamp and signatory on all evidence
- Hash chain or digital signature for integrity
- Retrievable by system, release, and control
- Versioned and immutable once published
- Access controlled and audit logged

**Evidence Required**:
- Evidence collection configuration
- Evidence validation records
- Evidence storage documentation
- Evidence retention records

### COMP-003: Audit Trail Maintenance

**Rule**: All significant system actions must be logged in an immutable audit trail.

**Why It Matters**: Audit trails provide evidence of system behavior, enable incident investigation, and support compliance requirements.

**Audit Trail Events**:
- Authentication events (login, logout, failure)
- Authorization decisions (access granted, denied)
- Data access events (read, write, delete)
- Configuration changes
- Release decisions
- Incident events
- Policy violations

**Implementation Requirements**:
- Log all significant events with required fields
- Protect audit trail integrity (hash chain, signatures)
- Retain audit trail per compliance requirements
- Make audit trail searchable for investigations
- Restrict audit trail access to authorized personnel
- Monitor audit trail for gaps

**Audit Trail Fields**:
- Event type
- Timestamp (UTC)
- User identity
- Source IP
- Action performed
- Resource affected
- Result (success/failure)
- Correlation ID

**Evidence Required**:
- Audit trail configuration
- Sample audit logs
- Integrity protection documentation
- Retention policy documentation

## P1 High Priority Rules

### COMP-004: Exception Register

**Rule**: All exceptions to compliance requirements must be documented in an exception register with owner, rationale, and expiration.

**Why It Matters**: Exceptions are acceptable when properly managed. Without a register, exceptions accumulate, are forgotten, and create compliance gaps.

**Exception Register Fields**:
- Exception ID
- Control ID and name
- Exception type (technical, resource, vendor, regulatory)
- Description and rationale
- Compensating controls
- Risk assessment
- Owner
- Approver
- Expiration date
- Status (proposed, active, expired, closed)

**Implementation Requirements**:
- Maintain exception register
- Require approval for new exceptions
- Track exception expiration
- Review exceptions quarterly
- Renew exceptions before expiration
- Close expired exceptions

**Exception Lifecycle**:
1. Exception requested with rationale
2. Risk assessment conducted
3. Compensating controls defined
4. Approval obtained
5. Exception granted with conditions
6. Exception monitored
7. Exception reviewed before expiration
8. Exception renewed or closed

**Evidence Required**:
- Exception register
- Exception approval records
- Exception review records
- Exception closure records

### COMP-005: Policy Documentation

**Rule**: All compliance policies must be documented, approved, and communicated to relevant personnel.

**Why It Matters**: Policies provide the basis for compliance. Without documented policies, expectations are unclear and enforcement is inconsistent.

**Policy Types**:
- Data protection policy
- Security policy
- Acceptable use policy
- Incident response policy
- Retention policy
- Access control policy
- Vendor management policy

**Implementation Requirements**:
- Document policies with clear requirements
- Obtain policy approval from authority
- Communicate policies to affected personnel
- Track policy acknowledgment
- Review and update policies regularly
- Archive previous policy versions

**Evidence Required**:
- Policy documents
- Approval records
- Communication records
- Acknowledgment records
- Review history

### COMP-006: Training Tracking

**Rule**: Compliance training must be assigned, completed, and tracked for all relevant personnel.

**Why It Matters**: Policies are only effective if people understand and follow them. Training ensures personnel know their responsibilities.

**Training Topics**:
- Data protection and privacy
- Security awareness
- Incident response
- Acceptable use
- Regulatory requirements
- Role-specific compliance

**Implementation Requirements**:
- Define training requirements by role
- Assign training to personnel
- Track training completion
- Remind personnel of overdue training
- Assess training effectiveness
- Update training based on incidents

**Evidence Required**:
- Training curriculum
- Training assignments
- Completion records
- Effectiveness assessment

## P2 Medium Priority Rules

### COMP-007: Vendor Management

**Rule**: Third-party vendors must be assessed for compliance and monitored throughout the relationship.

**Why It Matters**: Vendors extend your compliance boundary. Vendor non-compliance can become your non-compliance.

**Vendor Assessment Areas**:
- Security posture
- Data protection practices
- Regulatory compliance
- Contractual obligations
- Incident response capability
- Financial stability

**Implementation Requirements**:
- Assess vendor before engagement
- Include compliance requirements in contracts
- Monitor vendor compliance
- Review vendor attestation regularly
- Handle vendor incidents
- Plan vendor exit strategy

**Evidence Required**:
- Vendor assessment records
- Contract compliance clauses
- Monitoring records
- Attestation records

### COMP-008: Regulatory Monitoring

**Rule**: Regulatory changes must be monitored and their impact on AI systems assessed.

**Why It Matters**: Regulations evolve. Without monitoring, systems may become non-compliant due to regulatory changes.

**Monitoring Activities**:
- Track regulatory announcements
- Assess impact on AI systems
- Update compliance requirements
- Implement necessary changes
- Document change assessment
- Communicate changes to stakeholders

**Implementation Requirements**:
- Establish regulatory monitoring process
- Assign responsibility for monitoring
- Assess impact of changes
- Update policies and procedures
- Implement required changes
- Document change management

**Evidence Required**:
- Monitoring process documentation
- Change assessment records
- Implementation records
- Communication records

## Compliance Anti-Patterns

### Checkbox Compliance

**Anti-Pattern**: Treating compliance as a checklist exercise without understanding the spirit of requirements.

**Why It Fails**: Checkbox compliance may satisfy auditors but doesn't actually protect the organization. It creates a false sense of security.

**Correct Approach**: Understand the purpose behind compliance requirements. Implement controls that address the actual risks. Focus on effectiveness, not just presence.

### Ignoring Exceptions

**Anti-Prompt**: Allowing exceptions to accumulate without tracking or review.

**Why It Fails**: Exceptions that are not tracked are forgotten. They create gaps that can be exploited or discovered in audits.

**Correct Approach**: Maintain exception register. Review exceptions regularly. Require approval for new exceptions. Close expired exceptions.

### Inadequate Evidence

**Anti-Pattern**: Collecting evidence that doesn't demonstrate control effectiveness.

**Why It Fails**: Auditors require evidence of effectiveness, not just presence. Inadequate evidence leads to audit findings.

**Correct Approach**: Define evidence requirements that demonstrate effectiveness. Collect evidence that shows controls work as intended. Validate evidence quality.

### Delayed Regulatory Response

**Anti-Pattern**: Ignoring regulatory changes until forced to respond.

**Why It Fails**: Delayed response can result in non-compliance, fines, and legal action. Proactive response reduces risk and cost.

**Correct Approach**: Monitor regulatory changes. Assess impact promptly. Implement changes within required timelines. Document change management.
